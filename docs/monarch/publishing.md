# Feature builds and publication

Use a separate `codex/` branch for each feature. Base each branch on the last accepted build, make the change,
run the repository checks, then create a signed APK and publish a phone-test candidate directly through GitHub
Releases. The owner explicitly does not want pull requests. A candidate can be promoted after phone testing.

## Build

Requirements: Node 24, the package.json-pinned pnpm version, Python 3, a JDK 17+ and Android SDK 36 with the
toolchain Expo requests. Run `pnpm install --frozen-lockfile`, set `JAVA_HOME` and `ANDROID_HOME`, then:

```powershell
.\scripts\build-apk.ps1 -BuildFolder 01-today-data-fix
```

For a later feature choose its own folder, update `app.json`'s `version` and `android.versionCode` and
`package.json`'s version, and write the notes into that folder before building.

`.release-signing/` contains this fork's persistent private key and its credentials. It must remain outside Git
and release attachments. Retain a private backup so future APKs can update existing installations. Build scripts
pass its values through environment variables; no secret is hard-coded in the Expo config plugin.

`android/` is generated by Expo and is not committed. Configuration changes go through app.json or config plugins.
On Windows the helper builds a public-source copy in `TEMP/monarch-build-<version>/` and uses pnpm's hoisted
node_modules layout to avoid AGP prefab batch-file path failures. The APK is copied back to the source build folder.
Gradle is fetched from its official server and checked against the published SHA-256 before use.

## Publish

APKs are Release assets, not Git blobs. The local build folder keeps the APK, checksum, notes and verification;
its markdown/checksum files are committed and its APK/logs are git-ignored.

After checks and APK verification, commit with the configured fork owner's Git identity and a signed-off
Conventional Commit. Push the feature branch, then publish the tested source commit directly without a pull request:

```powershell
python scripts/publish-release.py --check
python scripts/publish-release.py `
  --apk builds/01-today-data-fix/pulse-mobile-0.4.2-arm64.apk `
  --notes builds/01-today-data-fix/RELEASE-NOTES.md `
  --commit <verified-source-commit> `
  --name "Monarch 01 — today's data fix (phone test)"
```

The publisher uses the existing Git credential helper, verifies the authenticated account and target repository,
creates a prerelease for the app version, uploads the APK once and verifies the resulting asset. If publication
returns an uncertain error, inspect the release before retrying; the script does not overwrite existing assets.

Build 01's package is `in.portlabs.pulse.monarch`. The launcher name is Pulse Monarch. Its update feed points to
this fork. Prereleases are intentionally excluded by the existing updater until the tested candidate is promoted.
Upstream Pulse uses a different signing key/package and keeps its own database and permissions.
